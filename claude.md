# cleanvibe

## Project Description
A pip-installable Python CLI (`cleanvibe`) that scaffolds AI-assisted coding projects and launches Claude Code. Zero dependencies -- just stdlib.

## Architecture
```
cleanvibe/
├── cleanvibe/
│   ├── __init__.py      # Version string
│   ├── cli.py           # argparse-based CLI entry point (new/research/original/chat/clone/convert/replicate/doctor)
│   ├── scaffold.py      # Core logic: create_project(), clone_project(), convert_project()
│   ├── research.py      # research_project(): original-research scaffold (lit-review-first + report)
│   ├── original.py      # original_project(): research scaffold + topic-finding loop (uncertain topic)
│   ├── chat.py          # chat_project(): git-tracked conversation (ask-first, session logs committed by hook)
│   ├── doctor.py        # doctor(): read-only drift audit (run_checks → Finding list)
│   ├── arxiv.py         # stdlib arXiv/alphaxiv metadata fetch + parsing (zero-dep)
│   ├── clawrxiv.py      # stdlib clawRxiv (clawrxiv.io) JSON API fetch + parsing (zero-dep)
│   ├── replicate.py     # replicate_{project,clawrxiv_project,manual_project}(): per-paper replication
│   └── templates.py     # scaffold + research + replication templates (shared CLAUDE.md blocks: _CLAUDE_CORE_RULES/_WRITING_SECTION/_common_claude_tail)
├── tests/               # stdlib unittest, run by CI on win/mac/linux
├── docs/                # replication_framing.md (vision) + replication-examples/ (reference corpus)
├── pages/                # static GitHub Pages site (index.html/identity.css/CNAME → cleanvibe.emmaleonhart.com)
├── .github/workflows/
│   ├── ci.yml           # 3-OS x 2-py-version matrix
│   ├── pages.yml        # deploy pages/ to GitHub Pages
│   └── publish.yml      # PyPI publish on release
├── pyproject.toml       # Package metadata, [project.scripts] entry point
├── LICENSE              # MIT
├── README.md            # Human-facing docs
├── queue.md             # Active, delete-only work queue
├── todo.md              # Long-horizon backlog (abstract)
└── devlog.md            # Where "done" lives: dated entries + releases
```

## Key Decisions
- **Zero dependencies**: Uses only stdlib (argparse, pathlib, subprocess, platform). No click, no typer. Keeps install fast and reduces supply chain risk.
- **Cross-platform**: Windows launches claude in a new cmd window via `subprocess.Popen`. Unix uses `os.execlp` to replace the process.
- **Non-destructive cloning**: `cleanvibe clone` only injects files that are missing. Never overwrites.
- **`--dry-run` flag**: Shows what would happen without writing anything. Builds trust.
- **queue.md is part of the scaffold**: Every project gets a `queue.md` and a CLAUDE.md that enforces planning into queue.md before executing, mirroring it into the task tool, and updating it in the same commit as the work. See the reference repos at `../Sutra/`, `../SutraDB/`, `../shintowiki-scripts/` for the established convention.
- **todo.md as long-horizon backlog**: `todo.md` holds the project's abstract long-term horizons; `queue.md` holds the concrete executable steps. Items flow `todo.md` → `queue.md` → done. The bootstrap sequence creates `todo.md` between "write documentation" and "write the real queue" so the long-horizon picture exists *before* anything concrete is queued.
- **`data_lake/.gitkeep`**: The Python scaffold creates `data_lake/.gitkeep` eagerly (in `create_project` and clone/convert injection) so the directory exists from the first commit — a user can drop files straight into it before the bootstrap session ever runs. The bootstrap queue step 1 then just moves user-supplied files into the already-existing `data_lake/`.
- **`clone` is codebase onboarding, not bootstrapping**: `cleanvibe clone` clones an existing repo, creates a dedicated `cleanvibe-onboarding` branch (default branch untouched), and commits a *small* onboarding `queue.md` + `CLAUDE.md` there — **no `data_lake/`** (nothing was dropped in) and **no README overwrite**. CLAUDE.md/queue.md are *prepended* if they already exist (`_prepend_or_write`, newest-on-top), so re-running just layers a fresh block. The onboarding queue's job is to document the repo, make its docs accurate, rewrite the onboarding CLAUDE.md into the repo's *real* practices, add tests/CI if sparse, then hand off to the repo's own `todo.md`. This is intentionally distinct from `new` (fresh project) and `convert` (in-place, missing-only injection).
- **`cleanvibe research` — original-research mode (v1.12.0).** A fifth mode (`cleanvibe research <name>`, also `cleanvibe new <name> --research [--question Q]`) in `cleanvibe/research.py` (`research_project()`). It is `new` for *your own* investigation (not a replication), so it keeps everything `new` has — `data_lake/`, the three-cron playbook, `todo.md`→`queue.md`→`devlog.md` — and borrows two things from `replicate`: (1) an up-front **literature review** (agentic RAG) as the distinctive bootstrap step, committed under `literature/` (`REVIEW.md` + sources), done *before* any building; and (2) a published, **themed GitHub Pages report** under `docs/` (committed `index.html` with a warm "paper" light theme + dark-mode variant adapted from latent-space-cartography / http://latent-space.emmaleonhart.com/, plus `docs/report.pdf` built from `FINDINGS.md` by `.github/workflows/pages.yml`). The bootstrap queue is literature-review-first: start crons → triage `data_lake/` → define the research question (interview) → **literature review** → write `todo.md` → push to a **private** GitHub repo (v1.18.0; going public for Pages is the user's call) → replace bootstrap queue → work it. Research is extensive work, so — unlike replication, which is exempt — it KEEPS the three-cron playbook. The workflow/cron/emergency-stop behavior is shared through the vendored skills (`.claude/skills/`, from `cleanvibe/skills.py`) and the `SKILLS_POINTER` in CLAUDE.md. v1.12.0 shared it through `_CLAUDE_CORE_RULES` / `_WRITING_SECTION` / `_common_claude_tail` helpers, which v1.14.0 removed when the behaviors became skills. The themed `docs/index.html` is filled via `str.replace` of `__PROJECT_NAME__`/`__QUESTION__`/`__DATE__` (its CSS is full of `{` and `$`, so neither f-strings nor `string.Template` are safe).
- **`cleanvibe original` — research with an uncertain topic (v1.16.0).** A sixth mode (`cleanvibe original <name> [--area FIELD]`, also `cleanvibe new <name> --original`) in `cleanvibe/original.py` (`original_project()`). It is `cleanvibe research` for the case where the topic is **uncertain** — no fixed research question yet. It keeps everything `research` has (literature review, themed `docs/` report, three-cron playbook, `data_lake/`, the `todo.md`→`queue.md`→`devlog.md` loop) and **prepends a topic-finding loop**: bootstrap step 3 (before the literature review) explores the focus area with agentic search/RAG, drafts + scores candidate research questions, confirms the shortlist with the user, and converges on ONE — recorded under a committed `topics/` dir (`TOPICS.md`: candidates + scoring + chosen question + rationale). The seed is an **`--area`** (a field), not a `--question`; the question is what the loop discovers, so at scaffold time it is always the `_ORIGINAL_QUESTION_PLACEHOLDER` ("not yet chosen…") and the area falls back to `_ORIGINAL_AREA_PLACEHOLDER` ("open…"). It reuses the research deliverables wholesale — `RESEARCH_GITIGNORE`, `RESEARCH_PAGES_YML`, `CLEANVIBE_REPORT_CSS`, and the `_RESEARCH_INDEX_HTML` shell (via `original_index_html`) — so research/original/replication never drift on theme or CI. Templates: `original_{claude,readme,queue,index_html}` + `_topic_area` in `templates.py`. CLI: an `original` subparser with `--area`, and a `new --original` alias routed through a shared `_do_original` handler (checked before `--research`).
- **`cleanvibe chat` — a git-tracked conversation (v1.18.0).** A seventh mode (`cleanvibe chat [NAME] [--topic T]`) in `cleanvibe/chat.py` (`chat_project()`). Emma's framing: not really a chatbot, and not a software project; an agentic conversation about one topic, research-heavy and light on code, kept in a **private** repo so it can be resumed, searched and shared. It is the first step of a possible wider rework of cleanvibe toward general-purpose (not only development) use, leaning on asking the user (AskUserQuestion) and starting as a conversation. NAME is optional: with none it is `chat-YYYY-MM-DD` in the cwd, silently auto-suffixed (the user chose no name, like `replicate`). **Chat launches with Remote Control on, unnamed** (Emma: remote-control starts need no name). `templates.claude_command(prompt, remote_control)` builds `claude "<prompt>" --remote-control`. The flag goes AFTER the prompt because `--remote-control [name]` takes an optional value and would swallow a following prompt as the session name. `REMOTE_CONTROL_MODES = {"chat"}` also puts the flag in chat's `!runClaude.bat`. Scaffold: `CLAUDE.md` (ask-first rules, notes discipline, session-log + private-repo notes, shared `BEHAVIOR_RULES`), a lightweight `queue.md` whose item 1 is "ask the user what they are trying to do" with AskUserQuestion, `devlog.md`, `notes/`, `sessions/`, `data_lake/`, `scripts/` mentioned but not created. **Session logs are git-tracked:** `.claude/settings.json` (`templates.chat_settings_json()`) runs the committed stdlib hook script `.claude/hooks/save_session_log.py` (`templates.CHAT_SAVE_SESSION_LOG_PY`, a raw-string constant) on **Stop** (every response) and **SessionEnd** (`--push`). It reads the hook JSON on stdin (`transcript_path`, `session_id`), copies the transcript to `sessions/<date>_<session8>.jsonl`, renders `sessions/<date>_<session8>.md` (user/Claude text, one-line tool notes, AskUserQuestion questions + answers, mid-turn `queued_command` messages, system reminders and thinking dropped), and commits ONLY `sessions/` (`git commit -- sessions`, so anything else staged is left alone). SessionEnd pushes if there is an upstream. It always exits 0 (a hook that fails would disrupt the session). The command is `python3 "$CLAUDE_PROJECT_DIR/..." || python "$CLAUDE_PROJECT_DIR/..."` (Claude Code runs hooks through bash, including Git Bash on Windows). Verified live on Windows with a headless `claude -p` run in `tests/scratch/chat-smoke`.
- **`cleanvibe doctor` — read-only drift audit (v1.18.0).** `cleanvibe/doctor.py`. Eight checks, each a `check_*(root) -> list[Finding]` in the `CHECKS` tuple: `files`, `skills` (vendored copy vs `skills.SKILLS`), `queue-done` (ticked boxes / check marks / DONE / strikethrough in `queue.md`), `version` (queue pointer vs `pyproject.toml`), `devlog-tags` (every `v*` tag mentioned in `devlog.md`), `section-refs` (every CLAUDE.md section reference must name a real heading), `ci`, `pages-gate` (pre-v1.18.0 Pages workflow on a private repo). It never writes; exit 0 clean, 1 findings, 2 bad path. Output goes through `_say`, so a Windows console can't crash on a quoted ✓. There is **no `--fix`** yet: none of the findings has a fix safe enough to apply blind. **`tests/test_doctor.py` asserts a fresh scaffold of every mode audits clean.** That test is what caught the generator pointing `queue.md`/`todo.md` at CLAUDE.md sections that had moved into skills in v1.14.0; they now name the skills. Run `python -m cleanvibe.cli doctor .` on this repo before a release.
- **One shared report theme for BOTH research and replication (v1.13.0).** `templates.CLEANVIBE_REPORT_CSS` is the single source of truth for the cleanvibe report theme — the warm "paper" light theme + dark-mode variant adapted from latent-space-cartography, plus the color-coded `.status-badge` (green=replicated / red=failed / amber=insufficient-hardware / blue=in-progress). `research` inlines it into `docs/index.html` at scaffold time; `replicate` writes it to a committed `report-theme.css` (all four modes — arXiv/clawRxiv/URL/manual) and `REPLICATION_PAGES_YML` inlines it at build time into a themed, self-contained `site/index.html` with the status badge on top, driven by a `status` field in `paper.json` (default `"in-progress"`; allowed `in-progress`/`replicated`/`failed`/`insufficient-hardware`). Both modes still build a transportable `report.pdf`. The replication Pages build renders the FINDINGS body with `pandoc` (no `-s`), then wraps it (theme + badge) in a bash block — `jq` reads the status. This resolved the long-standing "prettier replication reports with a status badge" queue item: the badge + theme are the same identity across both report types. (Earlier templates referenced `sutra.emmaleonhart.com` as the site-shape vision; v1.13.0 switched the exemplar to `latent-space.emmaleonhart.com`, whose theme is now the default.)
- **Project website**: a dependency-free static site under `pages/` (vanilla HTML/CSS/JS: a what-it-is section, one searchable card per subcommand, the stability contract; `updates.md` is the skill update index that scaffolded repos read weekly) deployed by `.github/workflows/pages.yml`. When a subcommand is added or changed, update its card. Pages Source on the repo is set to "GitHub Actions".
- **`cleanvibe replicate` (sibling subcommand, dual-mode)**: `cleanvibe replicate <ref-or-folder>` scaffolds a *standalone* replication project for one paper (absorbed from the now-sunset `replication_skill` project). It is a sibling of `new`/`clone`/`convert`. The single positional argument dual-dispatches via `arxiv.is_arxiv_ref()`:
  - **arXiv mode** (arg parses as an arXiv/alphaxiv id or URL): fetch metadata, scaffold `replicating-<paper-slug>/` (default dir **silently** auto-suffixed `-2`/`-3` on collision — the user supplied no name, deliberately asymmetric with `cleanvibe new` which prompts), write `paper.json` + `download_paper.py`. `arxiv.parse_arxiv_id` accepts **any** arxiv/alphaxiv URL path (not just `abs|pdf|html` — alphaxiv's primary form is `/overview/<id>`, plus `/forum/`, versioned ids, trailing slug/query): for any arxiv/alphaxiv URL it extracts the first id-shaped token from anywhere in the string; the strict bare-id path is unchanged. (Before v1.3.0 only `/(abs|pdf|html)/` worked and the `ValueError` surfaced as a raw traceback — that was the "arXiv link replication not really working" bug.)
  - **manual drop-in mode** (arg is anything else → a folder name): NO metadata fetch, NO `download_paper.py`, NO `paper.json`, NO network. The user drops the paper PDF(s) into `replication_target/` and supporting material into `data_lake/` by hand; the manual templates (`replication_manual_{claude,queue,skill,readme}_md` in `templates.py`) say this up front and queue step 1 makes the agent STOP and ask for the paper rather than invent one. Injection is **non-destructive** (`scaffold._write_if_missing`) so running on a folder that already holds the dropped paper / a user README never clobbers it; it commits into an existing git repo or git-inits a fresh one.
  - Shared structure (both modes): the paper lives under `replication_target/` (gitignored — copyrighted/local input, **never** in `data_lake/`); `data_lake/` exists for other material; the authors' code is cloned as a git submodule under `replication_target/`; deliverables (GitHub Pages site + transportable PDF report + downloadable ZIP package) are built by GitHub Actions, not committed. arXiv access is stdlib `urllib` only (zero-dep guarantee); arXiv-mode replication templates are inline `string.Template` constants, manual-mode templates are plain f-string functions (both no package data). Long-horizon replication-infrastructure work is in `todo.md`; framing/vision in `docs/replication_framing.md` with a reference corpus under `docs/replication-examples/`.
- **Source-first + recipe-first replication architecture (v1.5.0).** The v1.4.0 live Sutra run *succeeded but was wasteful*: it downloaded the HTML (and had to hand-strip base64 figure blobs), reimplemented everything from scratch, and only noticed the paper's own reproduction recipe late — and it never pushed to a remote. v1.5.0 restructures the generated arXiv scaffold so the efficient path is the default:
  - **`download_paper.py` fetches the arXiv LaTeX/e-print source** (`arxiv.org/src/<id>`) and extracts it to `replication_target/source/` (committed; the raw `arxiv-source.tar.gz` is gitignored), PDF as fallback. The `.tex` is far cheaper to read than the base64-laden HTML. Robust to the three arXiv source shapes (gzip-tar / single-gzip-tex / PDF-only) via stdlib `tarfile`/`gzip`, with a safe-extraction guard and `filter="data"` on Python 3.12+. It also flags candidate recipe filenames.
  - **Recipe-first ordering.** The generated `queue.md`/`SKILL.md` put "find + run the authors' reproduction recipe" at the FRONT, before any deep paper analysis (a recipe is usually shipped right in the paper source, near the end). A found recipe file is copied to `replication_skill.md`; a referenced replication zip is extracted into `replication/` (zip gitignored). Then verify the recipe's output against the paper, **check ALL references in every run**, and reimplement only the gaps.
  - **Go live early.** The queue/SKILL tell the agent to `gh repo create --private --source=. --push` near the start (private since v1.18.0) so every commit pushes and CI builds as the work goes — the v1.4.0 run stayed local-only. Validated against Sutra: grepping the extracted `.tex` immediately surfaces the repo URL, a `sutra-replication-package.zip`, and a shipped `SKILL.md`.
- **clawRxiv as a first-class replication source (v1.6.0).** clawRxiv (clawrxiv.io) publishes papers authored autonomously by AI agents and exposes a JSON API (`/api/abs/<id>`) that **differentiates the paper content, abstract, and skill file** (`content` / `abstract` / `skillMd`) — the purest recipe-first case, so it gets its own `replicate` mode distinct from arXiv/alphaxiv.
  - `cleanvibe/clawrxiv.py`: `ClawrxivPaper` + `is_clawrxiv_ref` / `parse_clawrxiv_id` / `fetch_clawrxiv_paper` (stdlib `urllib`+`json`, light 429/503 retry). Accepts `clawrxiv.io/{abs,api/abs}/<id>` (with/without `www.`) and `clawrxiv:<id>`. clawRxiv ids are arXiv-shaped, so a **bare id stays arXiv** — clawRxiv needs an explicit signal. The CLI checks `is_clawrxiv_ref` **before** `is_arxiv_ref`.
  - `replicate_clawrxiv_project` writes a **skill-first** scaffold: paper content → `replication_target/source/paper.md` (committed), skill recipe → `replication_skill.md` (only when `skillMd` is a separate field; otherwise the queue tells the agent to extract the recipe embedded in `paper.md`). `paper.json` records `source: "clawrxiv"` + `has_skill_file`. **No `download_paper.py`** — the API returns everything in one call. Templates: `clawrxiv_{claude,queue,skill,readme}_md` + `_clawrxiv_subs` in `templates.py`; gitignore + workflow constants reused. Validated live against `clawrxiv:2605.02609` (ROMO-CV; `skillMd` null → embedded path exercised).
- **Windows launcher renamed `runclaude.bat` → `!runClaude.bat` (v1.6.0).** The `!` floats it to the top of the file listing (easy to find) and camelCase reads cleanly; it stays an executable `.bat` (double-click launches Claude). Written by `new`/`convert`/`clone`/`replicate` (all modes). Historical devlog entries keep the old name as a record.
- **The paper is NEVER committed — `replication_target/` is fully gitignored (v1.15.0, copyright fix).** This reverses the v1.6.1 "commit 2 extracts + commits the source" decision below, which was a copyright violation: scaffolding a replication committed the paper's text (extracted arXiv LaTeX `source/`, clawRxiv `paper.md`, downloaded URL source) into the repo, redistributing a copyrighted work. The contract is now: `download_paper.py` deterministically populates `replication_target/` **locally only**, the **whole directory is gitignored** (`REPLICATION_GITIGNORE` is `replication_target/*` + `!replication_target/.gitkeep` — the `/*` form, not bare `replication_target/`, because git can't re-include `.gitkeep` under a directory ignored outright), and if the directory is empty (e.g. a fresh clone) the agent/user re-runs the downloader. Concretely: `_run_extraction_commit` → `_run_extraction` (runs the downloader to populate locally, **commits nothing**); arXiv keeps its `download_paper.py`; **clawRxiv and URL modes gained their own `download_paper.py`** (`clawrxiv_download_paper_py` re-fetches `content` from the clawRxiv API; `url_download_paper_py` re-downloads from the URL recorded in `source.json`) so an empty `replication_target/` is always repopulatable. Only the *root* `replication_skill.md` (a recipe, not the paper) and the authors' code as a **submodule** (`git submodule add -f …` — `-f` because the path is gitignored; only the gitlink is committed) are committed. Manual drop-in mode was already correct (paper dropped in by hand, gitignored). Every `replicate` template's prose was updated from "source/ is committed" to "gitignored, local context only; run `download_paper.py` if empty".
- **Consent gate + commit-2 source extraction (v1.6.1; the commit-2 half was reversed in v1.15.0 — see above).** Two coupled changes so replication is both more turnkey AND safer:
  - **~~Commit 2 happens in the scaffolder (arXiv mode).~~** *(Superseded by v1.15.0: the source is still downloaded + extracted locally before launch via `_run_extraction`, but it is NEVER committed — the paper is copyrighted.)* After the framework commit, `replicate_project` runs the just-written `download_paper.py` (`_run_extraction`) to download + extract the e-print source into the gitignored `replication_target/source/`, **before launching Claude** — the agent opens onto an already-extracted paper. Best-effort (network failure → warns, leaves it for the agent), gated by an `extract` param (`True` from the CLI; tests pass `False` to stay network-free). This is data download + tarball extraction by cleanvibe's own stdlib code, NOT third-party execution, so it is not consent-gated.
  - **Consent gate is queue step 1.** Because replication *runs code the user didn't write* (the authors' recipe / cloned scripts / a downloaded zip), the generated `queue.md` (arXiv + clawRxiv) and the manual queue now make the agent **STOP and get explicit user consent before executing ANY external/cloned code** — reading the paper/source/recipe is fine; *running* third-party code is the gated action. Reinforced in the SKILL plans and a future automated security-scan item is logged in `todo.md`. For now: ask the user; only replicate trusted sources.
- **`devlog.md` — "done" lives here, so `queue.md` can stay delete-only.** Every cleanvibe-scaffolded project (and this repo) ships a `devlog.md`. Finishing a queue item = delete the item from `queue.md` AND append a dated entry to `devlog.md` in the same commit, then push. Never tick boxes in place — a checked box left in `queue.md` is the failure mode this file exists to prevent. Releases (tag + one-line note) and notable milestones also live in `devlog.md`. `cleanvibe new` and `cleanvibe replicate` write a starter entry; `cleanvibe clone` and `cleanvibe convert` inject a "backfill from `git log`" variant whose first onboarding task is to catch the existing repo's devlog up to present before normal work resumes. Flow: `todo.md` (abstract) → `queue.md` (concrete steps) → task tool (in-flight) → `devlog.md` + `git log` (history).
- **PyPI packaging**: `pyproject.toml` declares `[tool.setuptools] packages = ["cleanvibe"]` explicitly. Without this, setuptools' flat-layout auto-discovery also picks up sibling directories like `site/` and `pages/` as candidate "packages" and refuses to build (caused the v1.0.0 PyPI publish to fail; fixed in v1.1.0).
- **Private repo by default in every mode (v1.18.0).** Emma reversed the earlier "go public for free Pages" default: every generated `gh repo create` is `--private`, and no template tells the agent to create a public repo (`tests/test_private_default.py` enforces it). Going public is the user's call; research/original ask it with AskUserQuestion at the go-live step. Both Pages workflows (`RESEARCH_PAGES_YML`, `REPLICATION_PAGES_YML`) gate `configure-pages` / `upload-pages-artifact` / the `deploy` job on `!github.event.repository.private || vars.CLEANVIBE_PAGES == 'true'`, because the free plan cannot publish Pages from a private repo and the deploy would otherwise fail on every push. They always upload the built report as a plain `report` workflow artifact, so a private repo still gets its PDF/site. A paid plan opts into Pages on a private repo with the repo variable `CLEANVIBE_PAGES=true`.
- **Starting prompt in every mode (v1.18.0).** `templates.starting_prompt(mode)` is the first message of every launched session: started with cleanvibe, which mode, what it is for, read CLAUDE.md + queue.md, work item 1, ask with AskUserQuestion if the goal is unclear. `_launch_claude(path, prompt)` passes it (`cmd /k claude "<prompt>"` on Windows, `execlp` elsewhere) and `runclaude_bat(mode)` bakes it into `!runClaude.bat`. It travels through cmd.exe/batch, so `starting_prompt` rejects `" % ^ & | < > !` and newlines.
- **Default branch is `main`, not `master`**: every cleanvibe-init'd repo (`new` / `convert` / `replicate`) passes `git init -b main` so the initial branch is `main` regardless of the user's `init.defaultBranch` config. Requires git ≥ 2.28 (mid-2020). Fixed in v1.1.1; older cleanvibe-scaffolded repos may need a one-time `git branch -m master main`.
- **Python 3.9 compat**: any module that uses PEP 604 unions (`X | None`) or PEP 585 generics (`list[str]`) in annotations must include `from __future__ import annotations` at the top — otherwise it fails at import on 3.9 (CI matrix target). `cli.py`, `arxiv.py`, and `templates.py` all carry the future import.

## Skills

cleanvibe dogfoods its own skills: the workflow behaviors live as skills in
`.claude/skills/` (auto-discovered by Claude Code) — `emergency-stop`,
`cron-is-local`, `autonomous-loop`, `queue-driven-workflow`, `writing-style`,
`cleanvibe-update-check`. They are the single-source-of-truth bodies from
`cleanvibe/skills.py`, materialized by `write_skills()`. The short version of the
workflow contract: commit early with *why*; plan into `queue.md` first and mirror
into the task tool; `todo.md` is the long-horizon basis for `queue.md`; finishing
an item = delete from `queue.md` + append a dated `devlog.md` entry in the same
commit, then push (never tick a box in place); keep this file, README.md, and
devlog.md current.

- **Last cleanvibe update check:** `never`
- **Updates source:** <https://cleanvibe.emmaleonhart.com/updates.md>

## Hourly status-report cron for extensive work
`queue.md`'s header and its pinned `## Always last` items point here. The source of
truth is the `autonomous-loop` skill (`.claude/skills/autonomous-loop/SKILL.md`);
this section is the short version for this repo. "The hourly status-report cron"
is the name this repo used before the playbook grew to three crons. It is now the
third of them.

- **When:** any session of relatively extensive work, above all one that fills
  `queue.md` with many items. Not for a one-off fix or a single small item.
- **What:** three session-local `CronCreate` jobs (`durable: false`; they die with
  the session, so every session recreates them), staggered so they don't collide:
  the **work-loop** at `:03` (sync, do the top actionable queue item, commit and
  push), the **auto-flush** at `:15` (commit and push anything pending, no empty
  commits), and the **status report** at `:42` (report only, no code changes:
  what advanced with shas, queue state, the hard rails, blockers tagged with the
  not-done taxonomy below, test health).
- **Lifecycle:** a fresh session **starts** the crons as its first move. A
  mid-session queue **re-fill** (a planning burst) makes its first item **kill**
  them. Entering planning mode **disables** them. Either way the queue's pinned
  tail closes the loop: (A) ensure the crons are running, starting or restarting
  them, then (B) run the status report once more as an end-of-session summary.
- The crons fire only while this machine and session are running. They are
  local, not cloud jobs (see the `cron-is-local` skill).

## Long command series run in strict order
When the user gives a long series of commands, treat it as a long series of commands to be
executed in relatively STRICT ORDER, one after another, EVEN IF the order seems not to make
sense or seems inefficient. The sequencing is intentional — the user organizes the steps so
states change in the order they want. Do not reorder, merge, or skip steps.

## Not-done taxonomy (never "deliberately deferred")
When work is NOT done, tag it with exactly ONE of: **NEEDS-DECISION** (name the decision +
who decides), **BLOCKED-ON-USER-ACTION** (a real-world action only the user can take — name
it), **BLOCKED-ON-EXTERNAL** (CI / a remote / a third party / another session's unpushed
commit — name it + the unblock signal), **NEEDS-INVESTIGATION** (not understood yet — a
to-do for the next tick, never a resting place), **UNSAFE-TO-GUESS** (could cause damage —
name the risk + what makes it safe), or **OUT-OF-SCOPE** (another repo's job — name it).
LOAD-BEARING DEFAULT: if it fits none of these with a specifically-named blocker, it is NOT
deferred — DO IT NOW. Bare "deliberately not done" / "blocked on <person>" is banned.

## Default replication target & live smoke tests
- **The default paper for `cleanvibe replicate` is arXiv:2605.20919 — "Sutra: Tensor-Op RNNs as a Compilation Target for Vector Symbolic Architectures"** (the maintainer's own paper). Use it whenever you need to exercise the `replicate` pipeline end-to-end against a real paper.
- **`tests/scratch/` is a gitignored sandbox for live `replicate` runs.** It is in `.gitignore`; never commit its contents. Each run scaffolds a full replication project (which git-inits its own nested repo) in there.
- The committed unit tests in `tests/` are network-free (they monkeypatch `fetch_paper`). A **live** smoke test actually hits arXiv, e.g.:
  ```
  python -m cleanvibe.cli replicate https://arxiv.org/abs/2605.20919 tests/scratch/replicating-sutra --no-claude
  ```
  Use `--no-claude` so it doesn't launch a Claude window, and an explicit path under `tests/scratch/`. To exercise the full source-first path, then run the generated downloader (`cd` into the scratch project and `python download_paper.py`): it fetches `arxiv.org/src/<id>`, extracts the `.tex` to `replication_target/source/` — local context only; the whole `replication_target/` is gitignored since v1.15.0 (the paper is copyrighted) — and prints any candidate recipe files.
- The full set of arXiv link forms the parser must accept (regression set): `https://arxiv.org/abs/<id>[vN]`, `/pdf/`, `/html/`, `/src/`, `https://doi.org/10.48550/arXiv.<id>`, `https://www.alphaxiv.org/{abs,overview,audio}/<id>`, bare `<id>[vN]`, and `arXiv:<id>`.
- **clawRxiv** (`cleanvibe/clawrxiv.py`): forms the parser must accept are `https://[www.]clawrxiv.io/abs/<id>`, `/api/abs/<id>`, and `clawrxiv:<id>`.
