# 07 — Did the 2.0.3 fixes work? The first eight 2.0.3 sessions

- **What it is:** the follow-up case study 06 asked for. The ai-context-research
  project re-ran its transcript extractor on the sessions that started after
  its corpus freeze (2026-10-01 00:00 UTC). There were 10: eight on cleanvibe
  2.0.3 (six projects, one of them with three sessions) and two still on 2.0.2,
  from the same days. The 2.0.2 pair is the control: same model and harness
  period, old tick prompt.
- **When:** sessions from 2026-10-01 to 2026-10-03; analysed 2026-10-03.
- **Privacy:** several of these sessions are personal conversations, so this
  write-up names no projects and quotes no one. The project-level evidence is
  in ai-context-research (`research/notes/post-freeze-m1-m8.md`).
- **Still no compaction** in any session, so M7's real test (constraints
  surviving a summary) has not happened yet.

## Method

The same extractor as 06, with a `--post-freeze` mode that adds per-tick
flags for the duties the 2.0.3 tick prompt names: read or edit INTENT.md,
edit README.md, run `date`, edit `queue.md`. A second script rebuilds each
project's committed `queue.md` at every tick, to see whether a tick that
found the queue empty refilled it. The behavioural rules (M3, M4, M5, M7, M8)
were coded blind by a fresh subagent from the raw transcripts, as six rules
R21–R26; two of its "violated" calls were re-checked against the transcripts
and held.

## What it found

| Fix | Result |
|---|---|
| M1, INTENT.md in the tick | Touched in 5/79 loop ticks (before: 4/143). Still 5–6 h stale in three sessions. **Not fixed.** |
| M1, README.md | Edited in 6/79 ticks (before: 1/169). Small, in the right direction. |
| M1, refill an empty queue | 0 of 55 empty-queue ticks refilled. Every one gave a reason (below). |
| M2, update check | Ran in 6/6 first sessions (before: 0/9; the one hit was the study reading the updates page). **Works.** |
| M3, times from the clock | `date` in 79/79 ticks, but also 24/26 in the 2.0.2 control, so that is a period effect. Blind coding: 5/8 sessions clean; all three lapses were estimated times written just after a `date` call. |
| M4, quote the user | 7/8. The one lapse took a stance from a garbled, dictated message while the user was there. |
| M5, downloads and memory | No session wrote to Claude Code's memory (before: two did). Downloads: 2/3 where it applied. |
| M6, `## Cron` in the log | Every cron fire rendered; none in the 2.0.2 control. **Works.** |
| M7, chat constraints into INTENT.md | 8/8. **Works.** |
| M8, prose through the file tools | 2/8. Six sessions still wrote prose with heredocs, `printf` or `>>`. **Not fixed.** |
| M8, check an edit before logging it | 4/8. Four logged an edit as done when it had failed or dropped content; one lost an open queue item. |

**The pattern:** INTENT.md is kept up to date when the user speaks (M7) and
left alone while the loop runs (M1). Rules that trigger at a clear event
(session start, a user message, a cron firing) now hold. Rules about how
every write is done (M8) do not, even though they are written in CLAUDE.md.

**The refill result is not a failure count.** The idle ticks said why:
- the research question was the agent's own guess and the open questions had
  been searched twice, so more work "would just be padding". That is 2.0.1's
  "a guess about why the project exists is not a task", and it beat M1;
- the remaining questions needed phone calls only the user could make;
- the only item left was a NEEDS-DECISION, while a second cron in the same
  session did the real work.

Two of the three are what cleanvibe wants. The first is a real conflict
between two rules.

## Open (Emma's decision)

- A checkable INTENT duty in the loop (a line in INTENT.md per tick, or the
  session-log hook flagging staleness), since naming it did not work.
- How far "refill the queue" should go on a question the agent only guessed.
- Whether M8 needs more than a CLAUDE.md line, e.g. a hook that warns when a
  shell command writes a `.md` file.
